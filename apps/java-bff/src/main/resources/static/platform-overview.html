结论

结论：作为作品与演示平台，这个底座可以打 8.5/10；作为生产系统，目前只有 5.5/10。差距不在 Agent 数量，而在多实例、安全、金标评测与运维闭环。

  1. 四个子 Agent 按同一协议接入，能力、Skills、确认与委托令牌已经打通。
  2. Java BFF、Python 编排、事件总线、Outbox 与飞轮形成完整闭环。
  3. 真实服务 E2E 101/101，Mock E2E 101/101，各层单元测试全部通过。
  4. 生产化仍缺 Kafka、多实例 SSE、SSO 与 PII、权限同步和金标评测。

适用于2026-11-26 快照本机真实服务分支 feat/base-hardening

一次请求如何穿过平台？

图的结构

  • 主 Java BFF 8600 main
  • Python AI 8700 ai
  • 物业 8200 property
  • 合同 8400 contract
  • OA 8810 oa
  • GIS Mock gis
  • MySQL 8 mysql
  • Redis Stream redis
  • MinIO minio
  • web → main · HTTPS / SSE
  • main → ai · 编排请求
  • main → property · 任务协议
  • main → contract · 任务协议
  • main → oa · 任务协议
  • main → gis · 能力查询
  • ai → redis · 事件总线
  • main → mysql · Outbox / 飞轮
  • main → minio · 附件

浏览器只认一个入口：主 Agent 的 8600。主 Agent 完成鉴权、路由和结果聚合，Python AI 负责规划与校验，子 Agent 只执行自己领域内的任务。

  1. 浏览器 H5 ↗

    发请求并订阅 SSE。

  2. 主 Java BFF 8600 ↗

    鉴权、路由、聚合结果。

  3. Python AI 8700 ↗

    规划、派发、收集、校验。

  4. 物业 8200 ↗

    返回任务视图与确认卡。

高风险动作不会直接执行。主 Agent 先返回 WAITING_CONFIRM，用户确认后再带服务端令牌重放请求。子 Agent 同时校验租户、角色和 dataScope，不信任主 Agent 的单点判断。

平台能力覆盖到什么程度？

能力域实现证据与边界
身份与权限JWT、RBAC、租户隔离网关校验，子 Agent 二次校验
Agent 动态安装Manifest 拉取与注册表版本、能力、Skills 自动同步
任务级 Skills四类 Agent 均声明物业 12、合同 6、OA 12
委托与签名委托令牌与 X-Identity-Assertion短时有效，绑定租户与端点
二次确认服务端确认令牌确认卡可读，令牌不落地前端
事件与可靠投递Redis Stream、Outbox、DLQ单机闭环，尚未上 Kafka
编排与路由LangGraph 五段式与混合路由规则优先，LLM 兜底
可观测健康、指标、编排审计未导出 Prometheus 或 OTel
飞轮与评测JSONL/MySQL 样本与离线评测未接金标集与 DPO
附件MinIO 上传与预览病毒扫描与配额未做

能力数量不是目标。真正决定可用性的是三条链路：skillId 能选对、确认令牌不能复用、失败任务能进 DLQ 并重放。这三条都已经有测试覆盖。

6

距离生产还差什么？

  • P0 多实例：把确认令牌、SSE 连接和幂等键迁到 Redis，支持双实例滚动发布。
  • P0 安全：接入 SSO/OIDC，补 PII 脱敏、审计留存和密钥轮换。
  • P1 消息：用 Kafka 替换 Redis Stream，保留 Outbox 与 DLQ 语义。
  • P1 权限：与 OA、物业的组织架构和 dataScope 定时同步。
  • P1 评测：建立金标集与人工抽检，分开统计集成通过率和业务正确率。
  • P2 检索：引入向量库与 Neo4j，补语义召回和知识图谱。
  • P2 运维：导出 Prometheus 指标，补告警、容量基线和发布回滚。

P0 不解决，系统只能单机演示。P1 决定能否多团队共用。P2 影响体验上限，但不阻塞上线。
