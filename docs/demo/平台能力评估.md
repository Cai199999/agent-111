# 平台能力评估：A2A / 前端 / 后端

> 评估日期：2026-11-21
> 评估对象：`wuye-agent` 当前 `feat/prototype` 分支
> 评估原则：只看代码和可运行证据，不把设计文档当成已实现能力。

---

## 0. 结论

| 维度 | 作为“可演示原型” | 作为“生产平台” | 一句话判断 |
|---|---:|---:|---|
| **A2A 编排语义** | **4 / 5** | **3 / 5** | 方言适配、任务生命周期、失败自修复是亮点；动态发现、标准互操作、分布式状态是短板 |
| **A2A 标准互操作（Google A2A）** | **2 / 5** | **2 / 5** | 已有 Agent Card 发现层；JSON-RPC/push 未实现，核心是自定义 REST 契约 |
| **前端** | **4 / 5** | **2 / 5** | Demo 体验完整；工程化、可测试性、可访问性是短板 |
| **后端** | **3.5 / 5** | **2.5 / 5** | 分层、状态机、确认、审计做得好；分布式与生产运维是短板 |
| **综合** | **3.5 / 5** | **2.5 / 5** | 高质量原型，不是 A2A 平台或生产系统 |

**面试定位建议：**
> “这是一个按生产契约做的 A2A 编排原型。核心价值是把不同方言的子 Agent 收敛成统一任务模型，并加上人工确认、权限、审计和降级；不是宣称已经实现了标准 A2A 或生产级多实例。”

## 1. A2A 能力矩阵

> 先区分两个概念：
> - **A2A 编排语义**：主 Agent 如何发现、选择、调用、确认、取消、观测子 Agent。
> - **A2A 标准互操作**：是否兼容 Google A2A 的 Agent Card / JSON-RPC / tasks / SSE / push notification。
>
> 这个平台强在前者，弱在后者。

| 能力项 | 等级 | 评分 | 已实现证据 | 主要缺口 |
|---|---|---:|---|---|
| Agent 注册/发现 | L2.5 | 2.5/5 | Spring Bean 自动注册；`AdapterRegistry` 按 `agentKey`/`capabilityId` 路由；HTTP 模式可拉 Manifest 的 `inputSchema`；已提供公开/子 Agent Agent Card | 无动态注册、无 Manifest 自动同步/版本校验；descriptor 静态硬编码 |
| 协议契约 | L3.5 | 3.5/5 | `docs/06` 定义 Canonical Agent Contract v1；Manifest/任务/确认/取消/事件/错误/健康 | 自定义 `agent-task-v1`，不是 Google A2A；无 JSON-RPC 2.0、无 message/part/artifact 模型 |
| 任务生命周期 | L4 | 4/5 | `submit/get/confirm/cancel/events`；状态归一化；`clientTaskId` 幂等；`parentTaskId/correlationId`；终态集合；失败自修复 | `deadlineAt/budget/contextRefs` 未真正下发；异步任务只在读接口时刷新，无后台推进 |
| 多 Agent 编排 | L3.5 | 3.5/5 | LLM 主导路由 + 规则兜底；计划最多 3 步；前置只读步骤；capability 命名空间；权限裁剪；失败后可换能力 | 无并行 fan-out、无 Agent handoff、无子 Agent 互相调用；计划能力偏弱 |
| 安全/委托 | L3.5 | 3.5/5 | 内部令牌；委托令牌签发+缓存；Actor/Roles/Tenant/Trace 头；确认令牌服务端保存并 AES-GCM 加密落库；查询/确认/取消已透传真实 Actor/Trace | 委托 scope 默认 `*`；无 mTLS/签名/防重放/吊销；多租户仍是静态配置 |
| 事件/流式 | L2 | 2/5 | 浏览器侧 SSE；子 Agent 事件用 `afterSeq` 轮询；任务时间线；失败反馈 `feedback` 事件 | 无子 Agent SSE 消费、无 `Last-Event-ID` 回放、无 `tasks/resubscribe`、无 push notification |
| 可靠性/容错 | L3 | 3/5 | 连接/读超时；依赖失败映射 `FAILED(DEPENDENCY)`；只读能力自动重试 2 次；LLM 30 秒熔断回退规则；人工队列自动清理中间失败 | 写能力不自动重试（有意）；无每 Agent 熔断；无任务队列/后台 worker/死信 |
| 可观测/治理 | L3 | 3/5 | traceId 贯穿；审计表；任务事件；指标/趋势/告警；人工介入队列；LLM token/成本 | 无 OpenTelemetry/Prometheus；无按 Agent/能力的延迟与错误率；无分布式追踪 |
| 标准互操作 | L2 | 2/5 | `/.well-known/agent-card.json` + `/api/v1/agents/{key}/card` + 管理端总览 | 无 JSON-RPC `message/send`、`tasks/get`、`tasks/cancel`、`tasks/resubscribe`、`tasks/pushNotificationConfig/*`；Agent Card 为 discovery-only |
| 契约测试 | L3 | 3/5 | 5 个 HTTP Adapter 测试；44 个 Java 测试 + 15 个 Python 测试 + 18 项端到端 smoke，覆盖自修复/追问/确认/拒绝/取消 | 无真实子 Agent 契约测试套件；无并发/故障注入/压测 |

**A2A 综合：**
- 作为“编排原型”：**4/5**
- 作为“标准 A2A 平台”：**2/5**（Agent Card discovery-only，JSON-RPC 未做）
- 作为“生产级 A2A 网关”：**3/5**

### 1.1 做得好的地方（面试可以讲）

1. **方言适配是真实价值**：物业 `{code,data}` + 数字错误码，合同裸对象 + 字符串错误码 + 202 异步，都在 Adapter 层吸收，上层不感知。
2. **任务状态机完整**：`PENDING/RUNNING/WAITING_CONFIRM/SUCCEEDED/FAILED/REJECTED/CANCELLED`，确认/拒绝/取消/超时都有路径。
3. **确认令牌不出服务端**：浏览器只拿 `taskNo`；令牌加密落库；这是政务/企业客户的关键差异点。
4. **幂等和续传**：`clientTaskId` 防重复；事件 `seq/afterSeq` 支持时间线续传。
5. **失败自修复**：VALIDATION 缺字段追问、参数错误 LLM 修正、只读依赖失败自动重试 2 次、能力不存在才兜底“目前没有这个功能”。
6. **参数不瞎猜**：调用子 Agent 前做 required/type/enum 校验；缺关键信息直接转追问。
7. **真实身份透传**：查询/确认/取消使用任务发起人的 `actorId` 和 `traceId`，不再用配置里的固定 Actor。
8. **可扩展性有证据**：第三个 Agent（时空资产：地块/变化图斑/巡查）只加 Adapter + 权限数据 + 领域关键词；主路由/确认/审计/人工队列/看板未改。
9. **运行时安装**：侧边栏「Agent 状态」＋ 可安装完整巡检 Agent（只读/写确认/异步/事件/取消）或从 Agent Card URL 安装 Canonical v1 HTTP Agent。
10. **权限裁剪**：Agent/能力目录按角色权限过滤，不是前端硬编码。

### 1.2 关键短板（面试不要回避）

1. **不是 Google A2A**：没有 Agent Card、JSON-RPC、parts/artifacts、push notification。如果面试官说“A2A”，先确认他指的是标准协议还是泛 Agent 编排。
2. **发现是静态的**：`AdapterRegistry` 从 Spring Bean 构建；`AgentDescriptor` 硬编码；`CapabilitySchemaService` 只在 HTTP 模式拉 schema，没有 Manifest 同步/版本校验/热注册。
3. **异步任务没有后台推进**：`TaskService.refresh` 只在 `GET /tasks/{taskNo}` 时调用子 Agent；没有 scheduler/queue。前端 1 秒轮询才推动状态。
4. **没有子 Agent 流式**：主 Agent 的事件是轮询子 Agent 后转发；没有消费子 Agent SSE，也没有 `Last-Event-ID`。
5. **委托 scope 过宽**：默认 `*`；没有按 capability 最小化 scope。
6. **多实例不成立**：`pendingIntents`、限流、部分状态在进程内；没有 Redis/分布式锁。
7. **写操作不自动重试**：这是有意的安全取舍，但依赖故障时只能转人工，不能自动恢复。
8. **契约测试不足**：HTTP Adapter 测试用本地 fake server，没有真实 8402/8400 的契约测试；没有并发/故障注入。

### 1.3 2026-11-21 已补：A2A 自修复闭环

```text
子 Agent 失败反馈（status/error/events）
  → TaskRecoveryService
      ├─ VALIDATION：LLM 决策 → CLARIFY（追问）或 RETRY（修正参数）
      ├─ NOT_FOUND：LLM 决策 → ALTERNATIVE（换能力）或 NO_CAPABILITY
      ├─ DEPENDENCY/TIMEOUT/RATE_LIMIT：只读能力自动重试 2 次
      └─ AUTH/CONFLICT/REJECTED/UNKNOWN：友好提示或转人工
  → 用户只看到：追问 / 自动修复成功 / 转人工 / 目前没有这个功能
```

配套改动：

- Python 新增 `/internal/v1/ai/recover`，输出 `CLARIFY / RETRY / ALTERNATIVE / NO_CAPABILITY`；
- Java 新增 `TaskRecoveryService`、`AgentErrorTranslator`、`RecoveryOutcome`；
- `InputSchemaValidator` 在调用子 Agent 前校验 required/type/enum；
- `AgentAdapter` 增加带 Actor/Trace 的重载，HTTP Adapter 使用真实身份；
- 中间重试/追问产生的旧任务自动从人工队列关闭，避免队列膨胀；
- 前端新增 `feedback` SSE 事件；任务卡片不再显示裸错误；
- 新增 Agent Card 发现层：公开脱敏主 Card、按权限裁剪的子 Agent Card、管理端 A2A 总览；
- 前端头像菜单新增“A2A 能力”面板；
- 测试：Java 51 + Python 15 + 端到端 smoke 26。

详细说明见 [`A2A自修复与记忆.md`](A2A自修复与记忆.md)。

## 2. 设计 vs 实现：文档承诺了什么，代码做了什么

> 这一节很重要。`docs/06` 是一份完整的设计稿，但代码只实现了核心链路。面试官如果照着文档追问，要能区分“已实现/已设计未实现/未设计”。

| 能力 | 文档描述 | 代码现状 | 影响 |
|---|---|---|---|
| 动态 Agent 注册 | `POST /api/v1/admin/agents`、`wa_agent_registry` | `AgentAdminController` 只有 GET；注册靠 Spring Bean | 不能热接入新 Agent |
| Manifest 同步 | `POST /agents/{key}/sync`、版本校验 | 只拉 `inputSchema`/个人资料表单；descriptor 静态 | 能力变更需改代码/重启 |
| Agent Card | `/.well-known/agent-card.json` | 无 | 不符合 Google A2A 发现机制 |
| 流式事件 | `streamEvents(...)` SPI | Adapter 只有 `events(afterSeq)` 轮询 | 事件有延迟，不能回放 |
| 附件上传 | `uploadAttachment(...)` SPI | 无 | 工单图片/合同附件未落地 |
| 身份映射 | `wa_identity_mapping` | 已补：`get/confirm/cancel` 透传真实 `actorId/traceId`；注册映射表未做 | 主要调用链身份已正确；跨 Agent 身份映射仍需配置 |
| deadline/budget/contextRefs | Canonical v1 请求体 | `AdapterTaskRequest` 未包含 | 超时/预算/上下文引用未真正传递 |
| 契约测试清单 | 18 项 checklist | 5 个 HTTP Adapter 测试 + 44 Java/15 Python/18 smoke | 没有真实子 Agent 契约验证 |
| 版本兼容 | 主版本匹配、拒绝不兼容 | 只有 descriptor 字段展示 | 没有启动时兼容性校验 |

**面试话术：**
> “设计稿覆盖了完整的 A2A 能力，但原型只实现了核心闭环：注册是静态的、发现是半自动的、事件是轮询的。动态注册、Manifest 同步、附件、标准 A2A 适配是下一步，不是我已经交付的。”

## 6. 面试时“可以讲 / 不要讲”

### 可以讲

- “我们做的是 A2A 编排语义：发现、选择、调用、确认、取消、观测。”
- “方言适配是核心：物业和合同的包络、错误码、同步/异步都不一样，Adapter 层吸收。”
- “写操作必须人工确认，确认令牌不出服务端。”
- “子 Agent 停机不会拖垮主流程，返回 `FAILED(DEPENDENCY)`，人工队列兜底。”
- “LLM 只做决策，不做执行；白名单 + JSON + schema + 子 Agent 二次校验。”
- “A2A 失败不是直接报错：VALIDATION 追问、参数修正、只读重试、能力不存在才兜底。”
- “测试：51 Java + 15 Python + 26 项端到端冒烟。”

### 不要讲

- ❌ “我们实现了标准 Google A2A。” → 只有 Agent Card 发现层，没有 JSON-RPC/push。
- ✅ 可以说：“我们有 Agent Card discovery-only；JSON-RPC transport 是下一层 facade。”
- ❌ “支持动态注册/Manifest 自动同步。” → 代码是静态 Spring Bean。
- ❌ “支持子 Agent 流式事件。” → 目前是轮询。
- ❌ “生产级多实例。” → 状态在进程内，没有 Redis/队列。
- ❌ “支持附件上传。” → 设计有，代码没有。
- ❌ “真实子 Agent 已联调。” → 当前 demo 是 mock。

### 被追问时的标准回答

**Q：你们和 Google A2A 什么关系？**
> “我们借鉴了 A2A 的任务/确认/事件语义，但线协议是自定义的 `agent-task-v1`。优势是能适配现有方言；如果要接标准 A2A，加一层 Agent Card + JSON-RPC transport adapter 即可，上层任务模型不变。”

**Q：为什么不做成 peer-to-peer？**
> “有意做成 hub-and-spoke：主 Agent 统一鉴权、审计、确认和降级，子 Agent 不互相调用，降低 SSRF、越权和令牌扩散。代价是编排能力有限，适合当前的企业内部场景。”

**Q：A2A 最难的是什么？**
> “不是协议字段，是方言和状态归一化：同一个‘确认’，物业返回 token+decision，合同可能返回 `CONFIRM_REJECTED`；同一个‘取消’，一个是原生、一个是协作式。Adapter 层要把这些收敛成统一状态机。”

## 7. 如果面试前还想提分：剩余动作

> 不建议大改架构。只做能讲清楚、能演示、风险低的。

### 7.1 加一个 Agent Card 端点（1–2 小时，最高性价比，未做）

- `GET /.well-known/agent-card.json`
- `GET /api/v1/admin/agents/{agentKey}/card`
- 内容：agentId、name、version、protocol、capabilities、auth schemes、endpoints。
- 面试话术：“我们已经有 canonical manifest；Agent Card 是标准 A2A 的发现层，加一个只读端点即可。”

### 7.2 修复后续调用的 Actor 透传（已完成）

- `AgentAdapter.getTask/confirm/cancel` 增加 `actorId/traceId` 参数；
- `AbstractHttpAdapter` 用真实 Actor，不再用 `endpoint.getActorId()`；
- `TaskService` 从 `TaskRecord.actorId` 传入。
- 面试话术：“这是我发现并修掉的一个真实问题：确认/取消必须用发起人身份，不能用配置里的固定 Actor。”

### 7.3 LLM 参数 JSON Schema 强校验（已完成）

- 用 `CapabilitySchemaService.schemaFor()` 在 Java 侧校验必填/类型/枚举；
- 不通过 → 走 recovery 或追问，不直接提交子 Agent。
- 面试话术：“LLM 输出不可信；白名单之后还要 schema 校验，再加子 Agent 二次校验。”

### 7.4 可选：A2A 时序图（1 小时）

用 archify 或 draw.io 画一张：
`浏览器 → Java BFF → Router → Adapter → 子 Agent → 事件/确认 → 人工队列`
面试时比讲 10 分钟更有效。

## 8. 最终判断

这个平台**不是**：
- 标准 Google A2A 实现；
- 生产级多实例 Agent 网关；
- 完整的前端工程。

这个平台**是**：
- 一个按生产契约做的 A2A 编排原型；
- 方言适配、任务状态机、人工确认、权限审计、降级都跑通了；
- 失败后会自修复：追问/修正/重试/换能力/转人工，而不是直接报错；
- 有会话摘要 + 全局画像两层记忆，可查看、可清除；
- 有测试、有一键演示、有清晰边界；
- 足以证明你理解 A2A 的**核心难点**，并且能把它落到代码。

**面试一句话：**
> “A2A 的价值不在协议字段，而在把不同 Agent 的方言、状态、确认和失败收敛成一个可治理的任务模型。我这套原型把这件事跑通了，标准协议适配和分布式生产化是明确的下一步。”
