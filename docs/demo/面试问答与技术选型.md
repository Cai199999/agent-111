# 面试问答与技术选型（苍穹数码）

> 用途：面试前 30 分钟速记。
> 原则：先讲业务断点，再讲架构取舍；主动说边界，不把原型说成生产系统。

---

## 0. 30 秒项目介绍

> “这是一个 Java BFF + Python 推理的智能体编排原型。用户在一个对话框里说人话，主 Agent 负责理解、补参、路由到物业/合同/时空资产等子 Agent；写操作必须人工确认，失败/拒绝自动进人工队列；全程有权限、审计、token 成本和运行指标。物业只是验证场景，换掉子 Agent 和主数据，这套底座可以复用到自然资源、城市治理、遥感复核。”

---

## 1. 技术栈全景

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言 | Java 21 + Python 3.13 | Java 稳企业能力；Python 做 LLM/算法生态 |
| 后端框架 | Spring Boot 3.5 | 成熟、易招人、生态全 |
| 持久化 | Spring JDBC + HikariCP + Flyway + MySQL 8 | SQL 可控、迁移透明、少 ORM 魔法 |
| 认证 | JWT（jjwt）+ BCrypt + RBAC 权限表 | 无状态、角色/权限可配置 |
| 前端 | 原生 HTML/CSS/JS + SSE | 零构建、演示快、依赖少 |
| AI 服务 | Python FastAPI + Uvicorn + OpenAI SDK | 接 DeepSeek/OpenAI 兼容模型 |
| 模型 | DeepSeek `deepseek-chat` | 中文好、成本低、OpenAI 兼容 |
| Agent 协议 | 自研 `agent-task-v1` REST + Adapter SPI | 兼容物业/合同方言；保留标准 A2A facade |
| 发现层 | Agent Card（`/.well-known/agent-card.json`） | 标准 A2A 发现语义，成本低 |
| 任务模型 | 状态机 + 确认令牌 + 事件 seq | 可确认、可取消、可追溯 |
| 异步/事件 | SSE + 轮询 + `afterSeq` | HTTP 友好、代理友好、可降级 |
| 安全 | 内部令牌 + 委托令牌 + AES-GCM + 限流 | 凭据集中、确认令牌不出服务端 |
| 可观测 | traceId + 审计表 + 指标/趋势/告警 + token 成本 | 能运营、能追责 |
| 记忆 | 会话摘要 + 全局画像 + `_memory` 注入 | 简单、可解释、不重复建记忆库 |
| 测试 | JUnit 5 + Mockito + JDK HttpServer + pytest + 自研 E2E | 无外部依赖、可重复 |
| 运行时 | 单机 Java + Python + MySQL | 面试演示足够；生产化再上 Redis/队列 |

## 2. 关键选型与取舍

### 2.1 为什么 Java BFF + Python AI，而不是全 Java 或全 Python？

**选择**：Java 负责鉴权、事务、任务状态机、审计、权限；Python 只做路由/解释/摘要/画像。

**为什么**：
- 企业能力（JWT、RBAC、确认令牌、审计、事务）Java 更成熟；
- LLM 生态、Prompt 迭代、模型 SDK Python 更快；
- HTTP 契约隔离，Python 不接触子 Agent 凭据和业务库。

**替代方案**：
- 全 Java（Spring AI / LangChain4j）：部署简单，但 Python 生态和模型兼容性弱一些；
- 全 Python：开发快，但企业鉴权/事务/并发治理要自己补；
- Node：前端统一，但企业后端生态不如 Java。

**取舍**：多语言带来契约、部署、延迟成本；换来职责清晰和风险隔离。

---

### 2.2 为什么 Spring JDBC，而不是 JPA/MyBatis？

**选择**：JdbcTemplate + Flyway。

**为什么**：
- SQL 完全可控，便于审计、排障、优化；
- Flyway 迁移透明，V1–V10 可追溯；
- 避免 JPA 的 N+1、懒加载、隐式更新；
- 原型表不多，手写映射成本可接受。

**替代方案**：
- JPA：CRUD 快，但复杂查询/性能调优容易踩坑；
- MyBatis：SQL 可控，但 XML/注解和映射文件更多；
- jOOQ：类型安全，但学习/生成成本高。

**取舍**：JdbcTemplate 有样板代码；换来可预测性和低魔法。

---

### 2.3 为什么只用 MySQL，没有 Redis/MinIO？

**选择**：MySQL 存会话/任务/事件/审计/画像；确认令牌 AES-GCM 加密落库。

**为什么**：
- 共享中间件只允许连接使用，不能改配置/重启；
- 演示规模下 MySQL 足够；
- 确认令牌加密落库，浏览器只拿 `taskNo`。

**替代方案**：
- Redis：确认令牌 TTL、限流、分布式锁更合适；生产化首选；
- MinIO：附件/合同文件需要；当前演示没有真实附件；
- Kafka/RabbitMQ：异步任务队列；当前用状态机 + 轮询。

**取舍**：进程内 `pendingIntents`、限流不是多实例方案；生产化必须补 Redis/队列。

---

### 2.4 为什么自研 `agent-task-v1`，不用 Google A2A/MCP/LangGraph？

**选择**：自定义 REST 契约 + Adapter SPI + Agent Card 发现层。

**为什么**：
- 物业/合同方言差异大（`{code,data}` vs 裸对象、数字 vs 字符串错误码、200/202）；
- 需要统一的确认、取消、审计、人工兜底，现成框架不直接给；
- 自研能快速适配现有系统，不被标准成熟度拖住。

**替代方案**：
- Google A2A：标准方向，但 JSON-RPC/Agent Card/push 完整落地重；当前只做 discovery-only；
- MCP：偏工具调用，不是完整任务生命周期/人工确认；
- LangGraph/AutoGen/CrewAI：编排灵活，但企业权限/审计/确认要另补；
- OSGi/插件：隔离强，但重。

**取舍**：不是标准协议，外部接入要适配；用“核心稳定 + 协议 facade”保留演进空间。

---

### 2.5 为什么 LLM 主导 + 规则兜底，而不是纯 LLM 或纯规则？

**选择**：HybridRouter：规则先给确定性结果，LLM 处理自然语言和复杂意图；LLM 不可用回退规则。

**为什么**：
- 纯规则对自然语言多样性太脆弱；
- 纯 LLM 有幻觉、延迟、成本和不可用风险；
- 规则能覆盖高频明确意图，LLM 覆盖长尾。

**替代方案**：
- 纯 LLM：体验好，但不可控；
- 纯规则：稳定，但用户必须说“机器话”；
- 微调小模型：特定领域更准，但需要标注数据和训练/运维。

**取舍**：两条路径增加复杂度；用 capability 白名单、schema、置信度阈值收敛。

---

### 2.6 为什么 JSON Prompt + 白名单 + Schema，而不是原生 Function Calling？

**选择**：LLM 只输出 JSON（capabilityId/args/confidence/plan），Java 侧校验。

**为什么**：
- 模型无关，DeepSeek/OpenAI 兼容端点都能用；
- 白名单防止编造能力；
- JSON Schema 校验必填/类型/枚举；
- 子 Agent 二次校验 + repair/recover。

**替代方案**：
- 原生 Function Calling：结构更稳，但厂商绑定、调试复杂；
- 约束解码：更强，但依赖模型/推理框架；
- 微调：领域准，但数据/成本高。

**取舍**：需要自己解析和修复；换来可移植和可审计。

---

### 2.7 为什么确认令牌放服务端，而不是浏览器/JWT？

**选择**：确认令牌只存服务端，AES-GCM 加密落库；浏览器只拿 `taskNo`。

**为什么**：
- 防止 token 泄露、重放、前端篡改；
- 写操作必须人确认，令牌绑定任务/Actor/能力/租户；
- 审计可追溯。

**替代方案**：
- 前端保存 token：实现简单，但泄露风险高；
- 无状态 JWT 确认：免存储，但撤销/一次性/重放难；
- Redis TTL：生产化更合适；当前 MySQL 加密落库。

**取舍**：服务端有状态；换来安全边界。

---

### 2.8 为什么 SSE + 轮询，而不是 WebSocket/消息队列？

**选择**：浏览器 SSE + 子 Agent 事件轮询（`afterSeq`），异步任务由前端轮询任务状态。

**为什么**：
- HTTP/代理/网关友好；
- SSE 足够单向推送；
- 轮询可降级，断线不影响任务状态；
- 不引额外中间件。

**替代方案**：
- WebSocket：双向、低延迟，但连接治理/扩容复杂；
- Kafka/RabbitMQ/Redis Streams：持久、可重放，但重；
- 子 Agent SSE：更实时，但当前未实现。

**取舍**：事件有延迟、前端轮询有负载；生产化可升级子 Agent SSE + 队列。

---

### 2.9 为什么原生前端，而不是 React/Vue？

**选择**：原生 HTML/CSS/JS，零构建。

**为什么**：
- 演示优先，加载快、依赖少；
- 单对话框 + 任务卡片 + 弹窗，原生足够；
- 避免构建工具和依赖升级风险。

**替代方案**：
- React/Vue：组件化、生态好、可测试；但构建/依赖/时间成本；
- 服务端模板：简单，但交互弱；
- 低代码：快，但定制/治理弱。

**取舍**：单文件 `app.js` 约 1500 行，可维护性/测试/可访问性弱；生产化应组件化 + E2E。

---

### 2.10 为什么动态安装是内存态，而不是 DB/OSGi/容器？

**选择**：`AdapterRegistry.register/unregister` + `AgentInstallService`，内存态。

**为什么**：
- 演示需要“点一下装上、点一下卸掉”；
- 不执行任意代码，只接 HTTP Agent Card；
- 不影响内置 Agent；重启后消失可接受。

**替代方案**：
- DB 持久化 + 启动恢复：生产化首选；
- OSGi/插件 jar：隔离强，但安全和运维重；
- 容器隔离：最强，但演示环境不现实。

**取舍**：重启丢失、多实例不一致；换来简单和安全。

---

### 2.11 为什么记忆放主 Agent，而不是每个子 Agent 一套？

**选择**：会话摘要 + 全局画像；动态 Agent 调用时注入 `_memory`。

**为什么**：
- 避免每个子 Agent 重复建记忆库；
- 统一治理、可查看、可清除；
- 子 Agent 只消费上下文，不持有敏感记忆。

**替代方案**：
- 每 Agent 独立记忆：灵活，但重复、难治理；
- 向量库/RAG：长期记忆更强，但成本和复杂度高；
- 全量历史：简单，但 token 成本高。

**取舍**：当前没有向量长期记忆/跨会话 RAG；生产化可加。

---

### 2.12 为什么批量用 `batch.execute`，而不是工作流引擎？

**选择**：主 Agent 工具 `batch.execute`，items 每项一个操作，逐项解析 ID、逐项确认。

**为什么**：
- 用户一次说多个工单，不能压成一个任务；
- 写操作仍逐项人工确认，安全；
- 无需引 Temporal/Camunda 等重引擎。

**替代方案**：
- 工作流引擎：持久、可重试、可视化，但重；
- 数据库批量 API：快，但语义/确认弱；
- 纯 LLM 拆解：灵活，但不稳定。

**取舍**：最多 5 项、顺序执行、无事务回滚；生产化可升级队列/工作流。

## 3. 遇到的问题、解决与替代方案

### 3.1 子 Agent 方言不一致

**现象**：物业 `{code,data}` + 数字错误码；合同裸对象 + 字符串错误码 + 202 异步。

**解决**：Adapter SPI；`AbstractHttpAdapter` 统一解析；状态/错误归一化；方言子类只提供 descriptor/endpoint。

**为什么**：不要求子 Agent 改造，主 Agent 吸收差异。

**替代**：强制统一协议（改造成本高）；ESB/网关（重）；每种方言写一套业务逻辑（耦合）。

---

### 3.2 LLM 编造能力/参数

**现象**：模型可能返回不存在的 capability、缺必填字段、类型错误。

**解决**：capability 白名单 + JSON-only + Schema 校验 + 子 Agent 二次校验 + repair/recover + 规则兜底 + 人工确认。

**为什么**：多层防护，任何一层都不假设 LLM 可信。

**替代**：只靠 Prompt（不可靠）；只靠子 Agent 校验（用户体验差）；微调（成本高）。

---

### 3.3 多轮补参/上下文丢失

**现象**：用户说“1栋大堂灯不亮”，缺工单类型；下一轮说“照明”，系统忘了上一轮。

**解决**：`PendingIntent` 按会话保存 capability/args/missingFields；sessionSummary + 全局画像；语义解析。

**为什么**：不重复问、不瞎猜。

**替代**：要求用户一次说全（体验差）；全量历史回放（token 成本）；向量记忆（重）。

---

### 3.4 确认令牌安全

**现象**：写操作不能自动执行；令牌不能给前端。

**解决**：服务端保存、AES-GCM 加密落库、绑定任务/Actor/能力、TTL、一次性；浏览器只拿 taskNo。

**为什么**：防泄露/重放/篡改。

**替代**：前端 token（不安全）；无状态 JWT（撤销难）；Redis（生产化）。

---

### 3.5 异步任务进度

**现象**：合同审查/巡检生成是异步；前端需要进度/事件。

**解决**：任务状态机 + 事件 `seq/afterSeq` + SSE + 轮询降级 + 取消。

**为什么**：HTTP 友好、可恢复。

**替代**：WebSocket（重）；消息队列（重）；子 Agent SSE（未实现）。

---

### 3.6 多工单批量反复追问

**现象**：“两个工单派两个人”被压成一个 assign，反复问 ticketNo。

**解决**：`batch.execute` + `HybridRouter` 确定性 batch + 逐项语义解析 + 多张确认卡。

**为什么**：不合并不同工单；写操作仍逐项确认。

**替代**：工作流引擎（重）；纯 LLM 拆解（不稳定）；要求用户分两次说（体验差）。

---

### 3.7 名称 → 内部 ID

**现象**：用户不会输入 ticketNo/parcelNo/contractId。

**解决**：`semanticResolve` 先只读查询；唯一命中自动合并；多个候选追问；查不到不猜；`mergeOutput` 支持单候选列表；workers 映射。

**为什么**：自然语言入口，编码只是兜底。

**替代**：要求编码（体验差）；模糊数据库搜索（越权/安全）；向量检索（重）。

---

### 3.8 平台目录追问丢上下文

**现象**：问“时空资产有什么功能”后，追问“具体是什么功能”又让用户选域。

**解决**：`platform.catalog` 支持 agentKey/keyword；`lastCatalogAgent` 记录聚焦 Agent；HybridRouter 对目录追问优先规则。

**为什么**：多轮对话要延续实体，不要每轮重新问。

**替代**：每轮都返回全部 Agent（噪音）；LLM 记忆（不稳定）。

---

### 3.9 动态安装不影响主流程

**现象**：新增 Agent 不能改主流程。

**解决**：Adapter SPI + Spring Bean/动态 register + capability 命名空间 + 权限 + Agent Card；动态安装/卸载。

**为什么**：新增成本在领域适配，不在平台改造。

**替代**：插件 OSGi（重）；每个 Agent 改路由/UI（耦合）；独立网关（多一跳）。

---

### 3.10 记忆统一注入

**现象**：动态 Agent 不应各建记忆库。

**解决**：主 Agent 注入 `_memory`（会话摘要 + 画像）；子 Agent 返回 `memoryUsed`。

**为什么**：统一治理、可解释、可清除。

**替代**：子 Agent 自己接向量库（重复/难治理）；全量历史（token 成本）。

---

### 3.11 演示稳定性 / LLM 抖动

**现象**：同一句话偶尔路由不同；E2E 有一次派单 ticketNo 抖动。

**解决**：固定演示话术；确定性规则兜底；E2E 多跑；离线 `DEMO_AI=0`；备份视频。

**为什么**：现场稳定优先。

**替代**：纯规则（体验差）；更强模型（成本/延迟）；人工兜底（不可规模化）。

---

### 3.12 测试与 E2E

**现象**：没有真实子 Agent，如何验证？

**解决**：JDK HttpServer fake 子 Agent、内存 profile、Spring Boot Test、pytest、自研 E2E（101 项）。

**为什么**：可重复、无外部依赖。

**替代**：Testcontainers（更真实，但重）；WireMock（成熟，但多依赖）；Playwright（浏览器 E2E，未做）。

## 4. 面试官可能问的问题

### 4.1 业务/产品

1. **为什么做这个项目？**
   - 业务断点：入口分散、信息不全、派单靠人、合同初审靠法务；
   - 选择标准：高频、规则可描述、数据可得、错误成本可控、有人工兜底。
2. **为什么先做物业？**
   - 角色清晰、任务高频、错误成本低，适合验证主 Agent + 子 Agent + 人工确认底座；
   - 不是只会做物业。
3. **怎么发现业务的？**
   - 跟岗/任务抽样/失败分析；没有真实跟岗就说“按方法拆解，真实项目需两周验证”。
4. **怎么衡量成功？**
   - 建单耗时、一次解决率、人工介入率、单任务成本、合同初审时长。
5. **怎么迁移到苍穹？**
   - 不动产登记、巡查执法、遥感复核、合同/成果审查；换子 Agent 和主数据，底座不变。

### 4.2 架构

6. **为什么 Java + Python？**（见 2.1）
7. **为什么不用 JPA？**（见 2.2）
8. **为什么不用 Redis/MinIO？**（见 2.3）
9. **为什么自研 A2A？**（见 2.4）
10. **怎么接一个新的 GIS/遥感 Agent？**
    - 实现 Adapter（或 HTTP Canonical v1）→ Manifest/Agent Card → capability 命名空间 → 权限 → 测试；
    - 主路由/确认/审计/看板复用。
11. **多 Agent 怎么避免死循环/越权/重复写？**
    - 白名单、权限、确认令牌、幂等 `clientTaskId`、状态机、超时/熔断、人工队列。
12. **怎么扩展？**
    - Agent 层五块：Registry/Discovery/Catalog/Adapter/Runtime；标准 Agent 零代码，方言 Agent 一个类。
13. **多租户？**
    - 表预留 tenant_id；独立库/前缀/bucket；当前单租户，生产化补隔离。
14. **为什么 hub-and-spoke，不是 peer-to-peer？**
    - 统一鉴权/审计/确认/降级；降低 SSRF/越权/令牌扩散；适合企业/政务。

### 4.3 AI

15. **LLM 幻觉怎么办？**（见 3.2）
16. **怎么评估路由准确率？**
    - 规则/LLM 对比集、置信度分布、人工抽检、E2E；当前靠测试和演示话术，生产化要标注集。
17. **Prompt Injection？**
    - 白名单、JSON-only、参数 schema、子 Agent 二次校验、写操作确认；系统提示与用户输入隔离；生产化加内容安全。
18. **为什么 DeepSeek？**

20. **记忆/RAG？**
    - 会话摘要 + 全局画像；无向量长期记忆；生产化加 RAG。
21. **Function Calling？**（见 2.6）

### 4.4 工程/安全

22. **确认令牌安全？**（见 3.4）
23. **幂等/重试/取消？**
    - `clientTaskId` 幂等；确认令牌一次性；取消协作式；依赖失败 `FAILED(DEPENDENCY)`；只读自动重试。
24. **异步任务怎么推进？**
    - 状态机 + 事件；当前前端轮询；生产化后台 worker/队列。
25. **可观测？**
    - traceId、审计、指标/趋势/告警、token/成本、人工介入率；生产化 OTel/Prometheus。
26. **测试？**
    - 66 Java + 15 Python + 26 smoke + 101 E2E；fake HTTP server；无真实子 Agent 契约测试/压测。
27. **CI/CD/部署？**
    - `ci.sh`、`backup.sh`、一键启动；未容器化；生产化要流水线/镜像/配置中心。
28. **限流/防刷？**
    - 进程内每用户/IP 300/min；生产化 Redis/网关。
29. **数据安全/私有化？**
    - 数据不出域、模型网关、敏感字段脱敏、RBAC/审计；生产化补密钥管理/网络隔离。
30. **前端为什么这么简单？**
    - 演示优先、零依赖；生产化组件化/E2E/CSP/可访问性。

### 4.5 GIS/苍穹

31. **你了解 GIS 平台吗？**
    - 诚实说了解边界；讲可迁移的 Agent 编排/权限/审计/人工确认；不装懂。
32. **GIS 分析怎么接？**
    - 只读工具：缓冲区、叠加、路径、点位查询；LLM 把自然语言翻译成参数；GeoJSON 结果；人工确认写操作。
33. **遥感变化检测怎么接？**
    - 异步子 Agent：图斑分级、相似案例、复核任务、报告草稿；人工复核留痕；影像不出域。
34. **为什么不用 PostGIS？**
    - 当前 GIS Agent 是 Mock；生产化用 PostGIS/GeoServer/ArcGIS；Adapter 层解耦。
35. **坐标系统/大数据/地图渲染？**
    - 当前未做；生产化由 GIS 引擎处理，Agent 只编排；前端可接 Cesium/OpenLayers/ArcGIS JS。
36. **私有化/离线？**
    - 模型可换本地/专有；数据不出域；Agent Card/HTTP 内网；审计/权限。
37. **你来了第一周做什么？**
    - 跟 3 个角色、抽 30 个任务、选 1 个高频低风险切口；两周做一条只读 Agent 纵向切片。

### 4.6 项目/行为

38. **最大难点？**
    - 方言归一化 + 确认安全 + LLM 不可靠；分别用 Adapter、服务端令牌、白名单/schema/兜底解决。
39. **如果重做？**
    - 更早做契约测试/真实子 Agent 联调；更早 Redis/队列；前端组件化；标准化 A2A facade。
40. **AI 写的代码怎么保证质量？**
    - 契约先行、测试门禁、小步提交、人工审查、线上可观测；AI 负责速度，我负责边界/验收。
41. **项目边界？**
    - Mock 子 Agent、无 Redis/MinIO、动态安装内存态、A2A discovery-only、无向量记忆、未压测。
42. **为什么离开/为什么苍穹？**
    - 结合真实动机；强调业务发现 + 全栈交付 + 平台化，不贬低前公司。
