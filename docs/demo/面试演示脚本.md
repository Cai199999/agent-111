## 一、演示定位：把物业讲成苍穹数码听得懂的故事

## 三、8 分钟主流程（照着点）

### 0. 登录（30 秒）

- 打开 `http://127.0.0.1:8600/`，用 `admin/admin123` 登录。
- 指一下右上角：`ADMIN` 角色、两个版本胶囊（物业 0.8.0 / 合同 0.7.0）；侧边栏有三个 Agent（物业、合同、时空资产）。
- 说：“权限不是前端写死的，菜单、Agent、能力卡片都来自后端的角色-权限表。”

### 1. 一句话查工单（1 分钟）

输入：

> 我有哪些待处理工单？

预期：

- 出现路由徽标：`物业 · 查询工单`、置信度、路由原因；
- 任务卡片展示 3 条工单；
- 下方有中文解释：“共返回 3 条工单……”。

讲解点：

> “路由由 LLM 主导，但只输出 capabilityId 和参数，不直接执行工具；规则路由作为不可用时的兜底。子 Agent 的原始返回保留在任务 API 里，聊天区做中文字段/枚举映射和自然语言解释，不改写数据。”

### 2. 自然语言建单 + 人工确认（2 分钟）

输入：

> 1栋大堂的灯不亮了

预期：

- 路由到 `property.ticket.create`，LLM 把“灯不亮”映射成 `LIGHTING`；
- 任务进入 `WAITING_CONFIRM`，弹出高风险确认卡片（报修内容、位置）；
- 点“确定” → `SUCCEEDED`，返回工单号 `GD202611200001`。

讲解点（这是全场最重要的 30 秒）：

> “写操作绝不自动执行。主 Agent 只负责准备参数，确认令牌只存服务端，浏览器看不到。用户确认后才调用子 Agent。这样既保留 LLM 的灵活性，又满足政务/企业客户对‘人负责’的要求。”

补充（可选）：点“取消/拒绝”一次，任务变 `REJECTED`，自动进入人工介入队列。这正好引出第 5 步。

### 2.5 自修复：不知道就问，不报错（1 分钟）

输入：

> 报修：花园的喷泉坏了

预期：

- Agent 不猜工单类型，直接追问：“请确认工单类型：照明、给排水、电梯、安防、保洁、其他？”；
- 回答“其他”后继续建单，进入确认卡片；
- 全程没有 `event:error`，没有裸字段名。

讲解点：

> “这不是 prompt 里写死‘缺字段就报错’。调用子 Agent 前先做 schema 校验；缺关键信息就追问，参数可修正就重试，能力不存在才兜底。子 Agent 的技术错误只留在事件和审计里，不给用户看。”

### 3. 派单/关闭工单（1 分钟）

输入任选其一：

> 把 GD20261119000107 派给 10002

> 关闭工单 GD20261119000107

预期：同样弹出确认卡片；确认后返回 `ASSIGNED` / `CLOSED`。

讲解点：

> “不同子 Agent 的方言不一样：物业是 `{code,data}` 包络、数字错误码；合同是裸对象、字符串错误码、异步 202。主 Agent 的 Adapter 层把它们归一化成统一任务状态，所以上层路由和 UI 不需要关心方言。”

### 4. 异步合同审查（1.5 分钟）

输入：

> 审查合同 HT-2026-001

预期：

- 任务先 `PENDING`，卡片显示进度/时间线；
- 约 1.5 秒后变 `SUCCEEDED`，返回“发现 3 个风险点”，`overall=FAIL`；
- 可展开任务事件（STATUS_CHANGED / PROGRESS / TOOL_CALL / DONE）。

讲解点：

> “合同审查是异步任务，主 Agent 自己掌握超时、重试、事件续传和取消；SSE 推事件，前端轮询降级。子 Agent 停机时返回 `FAILED(DEPENDENCY)`，主 Agent 不崩。”

### 4.5 可扩展性：第三个 Agent（1 分钟）

输入任选：

> 查询地块 P-2026-001

> 有哪些遥感变化图斑？

> 为地块 P-2026-001 创建巡查任务

预期：

- 侧边栏出现第三个 Agent：时空资产；
- 地块/图斑查询直接返回；
- 巡查任务弹出高风险确认卡，确认后 `SUCCEEDED`；
- 打开“A2A 能力”，能看到 `geo-asset-agent` 的 Card 和 3 个能力。

讲解点：

> “第三个 Agent 只加了一个 Adapter + 一份权限数据 + 几个领域关键词，主 Agent 的路由、确认、审计、人工队列、看板全部复用。这就是可扩展的多 Agent 平台：新增领域 Agent 的成本是领域适配，不是平台改造。”

### 5. 管理看板 + 人工介入 + 审计（1.5 分钟）

- 右上角头像 → **数据看板**：
  - 业务价值：自动化完成率、预计节省工时（按 8 分钟/单的演示假设）、单任务 LLM 成本；
  - 运行指标：任务总数、成功率、待确认、平均耗时、人工介入率、LLM 调用/token/成本、工单漏斗、能力分布。
- 头像 → **人工介入**：待确认/失败/拒绝任务自动入队；WORKER/ADMIN 可认领、处理、关闭。
- 头像 → **审计日志**：登录、任务提交、确认、取消、会话删除、工具调用都有记录。
- 头像 → **A2A 能力**：主 Agent Card、两个子 Agent Card、健康状态、能力列表、`discovery-only` 标记。

讲解点：

> “AI 系统要能运营：成功率、P95、人工介入率、token 成本、审计轨迹。这些不是后补的，是主 Agent 的一等公民。”
>
> “A2A 这块我做的是渐进架构：先把任务、确认、审计做成稳定内核，外部只加一层很薄的 Agent Card 发现层；JSON-RPC 传输是下一层 facade，接进来不影响内核。”

### 6. 收尾（30 秒）

> “整套东西是 Java 21 + Spring Boot 3.5 的 BFF，Python FastAPI 只做推理，MySQL 持久化，原生 HTML/JS + SSE。两个子 Agent 是 mock，但协议、鉴权、确认、事件、错误映射都是按真实子 Agent 契约写的；8402/8400 起来后切 `WUYE_AGENT_MODE=http` 就能活体联调。”

## 四、3 分钟架构讲解（如果面试官追问）

```
浏览器（原生 HTML/JS + SSE）
        |
        v
Java BFF（Spring Boot 3.5 / Java 21）
  - JWT + RBAC（角色-权限表驱动）
  - 会话/消息/任务/事件持久化（MySQL + Flyway）
  - 主 Agent：HybridRouter（LLM 主导 + 规则兜底）
  - Plan 拆解 / 多轮补参 / 参数修正
  - Adapter SPI：Mock / HTTP 方言适配
  - 确认令牌（服务端保存）/ 取消 / 超时
  - 审计 / 限流 / 指标 / 人工介入队列
        |                         |
        v                         v
Python FastAPI             子 Agent（物业 8402 / 合同 8400）
  - 只做路由/解释/摘要          - 真实业务与数据
  - 不持有子 Agent 令牌         - 独立库/缓存/对象存储
```

关键设计：

1. **LLM 只做决策，不做执行**：输出严格 JSON（capabilityId/args/confidence/plan），后端校验白名单和 schema。
2. **写操作必须人工确认**：确认令牌不出服务端；拒绝/失败/待确认进入人工队列。
3. **方言适配**：`{code,data}`、裸对象、数字/字符串错误码、200/202、同步/异步，都在 Adapter 层吸收。
4. **参数纠错闭环**：子 Agent 校验失败 → 错误回传 LLM → 修正参数 → 重试；仍失败则转人工。
5. **可观测**：traceId 贯穿、审计表、token/成本、成功率/P95、告警。
6. **可扩展**：新增 Agent = 实现 Adapter + 注册 Manifest + 命名空间化 capabilityId，不改主流程。

## 五、高频问答（背下来）

**Q1：为什么 Java + Python 两套？**
> Java 负责稳的东西：鉴权、事务、审计、权限、任务状态机；Python 负责模型生态和快速迭代。两边只通过 HTTP 契约通信，Python 不碰子 Agent 令牌和业务库。

**Q2：LLM 幻觉/乱调工具怎么办？**
> 四道闸：① 只能从 capability 白名单选；② 只输出 JSON，不输出代码/SQL；③ 后端按 inputSchema 校验必填和枚举；④ 子 Agent 二次校验，失败回传 LLM 修正；⑤ 写操作人工确认；⑥ LLM 不可用自动回退规则路由。

**Q3：怎么接一个新的 GIS/遥感 Agent？**
> 实现 Adapter（或直接用 HTTP 方言适配）→ 提供 Manifest（capabilityId、inputSchema、同步/异步、是否需要确认）→ 注册到 Registry。capabilityId 用命名空间避免冲突，比如 `gis.buffer.analyze`、`rs.change.detect`。主 Agent 的路由、权限、审计、确认自动复用。

**Q4：和苍穹的业务怎么结合？**
> 三个切入点：① 把 GIS 空间分析封装成只读工具（缓冲区、叠加、路径、点位查询），LLM 负责把“帮我看一下这个地块周边 500 米内的巡查事件”翻译成工具参数；② 遥感变化检测作为异步子 Agent，主 Agent 负责派发、进度、人工复核；③ 政策法规/测绘标准做 RAG 知识库，回答带出处。底座不变，换 Agent 和主数据即可。

**Q5：数据隔离/多租户？**
> 每项目独立库、Redis 前缀、MinIO bucket；表里预留 tenant_id。当前演示是单租户，但资源隔离边界是按多项目设计的。

**Q6：性能/稳定性？**
> SSE 流式返回；异步任务 + 事件续传 + 轮询降级；LLM 30 秒熔断回退规则；子 Agent 停机返回 `FAILED(DEPENDENCY)` 不拖垮主流程；限流按用户/IP；确认令牌服务端存储。

**Q7：这个项目你最想改进什么？**
> ① 子 Agent 目前是 mock，下一步做真实 8402/8400 活体联调；② 确认令牌从进程内迁 Redis；③ Manifest 自动同步/版本校验；④ 任务事件从轮询升级为完整 SSE；⑤ 加 OpenTelemetry/Prometheus；⑥ 接入真实 GIS 引擎和空间索引。

**Q8：你负责了哪些部分？**
> 按真实情况说。可以讲：整体架构、Agent 接入层、路由与补参、确认/审计/人工介入、前端单对话框、MySQL/Flyway、测试与 CI。不要夸大没做过的。

## 八、演示话术（30 秒版）

> “这是一个 Java BFF + Python 推理的智能体编排原型。用户在一个对话框里说人话，主 Agent 负责理解、拆解、补参、路由到物业/合同子 Agent；写操作必须人工确认，失败/拒绝自动进人工队列；全程有权限、审计、token 成本和运行指标。物业只是演示场景，换一个 GIS 或遥感子 Agent，这套底座可以直接复用。”
