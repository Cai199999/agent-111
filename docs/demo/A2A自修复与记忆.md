# A2A 自修复与记忆系统说明

> 目标：A2A 调用失败时不把技术错误甩给用户；能修复就自动修复，
> 缺关键信息就追问，确实没有能力才兜底说“目前没有这个功能”。

---

## 一、A2A 反馈闭环

```text
用户消息
  → 主 Agent 路由/补参
  → TaskService 提交子 Agent
  → 子 Agent 返回 status/output/error/events/confirmation
  → TaskRecoveryService 读取失败反馈
      ├─ VALIDATION       → LLM 决策：CLARIFY / RETRY（修正参数）
      ├─ NOT_FOUND        → LLM 决策：ALTERNATIVE / NO_CAPABILITY
      ├─ DEPENDENCY/TIMEOUT/RATE_LIMIT
      │     → 只读能力自动重试 2 次；写能力不自动重试
      ├─ AUTH/CONFLICT    → 友好提示，不暴露底层错误
      └─ REJECTED         → 尊重用户拒绝，可重新发起
  → 用户看到：追问 / 自动修复成功 / 转人工 / 目前没有这个功能
```

### 1.1 错误分类与用户反馈

| 错误分类 | 自动动作 | 用户看到 |
|---|---|---|
| `VALIDATION` | LLM 修正参数；缺必填字段则追问 | “我还需要确认一下：工单类型……能补充一下吗？” |
| `NOT_FOUND` / `CAPABILITY_NOT_FOUND` | LLM 尝试替代能力；没有则兜底 | “目前没有这个功能。我可以帮你查工单、建单、派单，或审查合同。” |
| `DEPENDENCY` | 只读能力重试 2 次；写能力不重试 | “子 Agent 暂时不可用，我已经重试过了。你可以稍后再试，或转人工。” |
| `TIMEOUT` | 只读重试；失败转人工 | “这次处理超时了，已转人工跟进。” |
| `RATE_LIMIT` | 只读重试；失败提示稍后 | “请求有点频繁，请稍后再试。” |
| `AUTH` | 不重试 | “当前账号没有这个权限，请联系管理员。” |
| `CONFLICT` | 不重试 | “任务状态已经变化，请刷新后重试。” |
| `REJECTED` | 不重试 | “你已拒绝这次操作。如果还需要继续，可以重新发起。” |
| 未知 | 转人工 | “这次没有处理成功，已记录并转人工跟进。” |

**技术错误去哪了？**
- 任务事件 `ERROR` 里保留原始 `message`；
- `wa_audit_log` 保留任务提交/确认/取消记录；
- 服务端日志保留 traceId；
- 前端任务卡片对 `ERROR` 事件只显示“处理遇到问题，已自动分析或转人工”，不显示裸错误。

### 1.2 不瞎猜：Schema 校验前置

`InputSchemaValidator` 在调用子 Agent 之前检查：

- `required` 必填字段；
- 基础类型（string/integer/number/boolean/array/object）；
- `enum` 候选值。

缺字段/类型错误 → 不调用子 Agent，直接进入自修复追问。
示例：`property.ticket.create` 缺 `ticketTypeCode` → 追问“工单类型”，而不是让子 Agent 返回 `ticketTypeCode不能为空`。

### 1.3 双向链路：Actor / Trace 透传

- 提交任务：`X-Actor-Id`、`X-Trace-Id`、`X-Correlation-Id`；
- 查询/确认/取消：使用任务发起人的真实 `actorId`，不再用配置里的固定 Actor；
- 子 Agent 的审计/授权能看到正确的人；
- 每次重试/替代能力都生成新任务，旧任务自动从人工队列关闭。

### 1.4 人工队列不膨胀

- 自动重试/自动修复的旧任务：`autoResolve`，备注“已自动重试/已自动修复”；
- 转为追问的旧任务：`autoResolve`，备注“已转为追问用户”；
- 只有最终仍失败、且需要人工处理的最后一个任务保留 `PENDING`；
- 用户拒绝的任务仍保留在队列，供人工复核。

## 二、记忆系统：有，但边界清晰

### 2.1 会话级摘要记忆（当前会话）

- 存储：`wa_chat_session.summary`；
- 生成：每轮对话后异步取最近 12 条消息，调用 LLM 生成摘要；
- 使用：仅当前会话路由时作为 `sessionSummary` 传入；
- 不跨会话检索，不写入全局知识库；
- API：`GET /api/v1/chat/sessions/{sessionNo}` 返回 `summary`。

### 2.2 全局用户画像（跨会话）

- 存储：`wa_user_memory_profile`；
- 内容：稳定偏好，例如默认项目/楼栋/房间、常用工单类型/优先级、常用意图、备注；
- 生成：会话摘要后异步抽取，置信度 ≥ 0.6 才写入；
- 使用：路由时作为 `userProfile` 传入，当前消息明确内容优先于画像；
- 显式工具：`memory.profile.update` / `memory.profile.get`；
- 个人中心可查看/清除：`GET/DELETE /api/v1/profile/memory`；
- 不保存姓名/电话/身份证等敏感个人信息。

### 2.3 还没有的

- 向量长期记忆 / 跨会话 RAG；
- 事实级记忆（“上次说的 3 栋漏水”这种事件记忆）；
- 记忆冲突消解/过期策略；
- 多租户记忆隔离（当前按 userId）。

**面试话术：**
> “记忆分两层：会话摘要解决当前对话的连续性，全局画像解决跨会话的稳定偏好。两者都异步生成、可查看可清除，不保存敏感个人信息。向量长期记忆和跨会话 RAG 是下一步，不是当前已交付的。”

## 三、面试演示建议

### 3.1 自修复演示（30 秒）

输入：

> 报修：花园的喷泉坏了

预期：
- Agent 不猜类型，直接追问“请确认工单类型：照明、给排水、电梯、安防、保洁、其他？”；
- 用户回答“其他”后继续建单，进入确认卡片。

讲解：
> “这里不是在 prompt 里写死‘缺字段就报错’，而是 schema 校验 + 自修复决策：缺关键信息追问，参数可修正就重试，能力不存在才兜底。”

### 3.2 依赖故障演示（如果现场方便）

把 `WUYE_AGENT_MODE=http` 指向一个未启动的子 Agent，问“我有哪些待处理工单？”：

- 主 Agent 自动重试 2 次；
- 仍失败 → “子 Agent 暂时不可用，我已经重试过了。你可以稍后再试，或转人工。”
- 任务自动进人工队列，用户看不到 `ConnectException`。

### 3.3 记忆演示（30 秒）

- 说“记住我默认 1 栋 101”，下一轮建单会自动带出项目/楼栋/房间；
- 个人中心 → 记忆 → 查看/清除；
- 新会话仍能使用全局画像，但不会读取旧会话原文。

## 四、边界与下一步

已做：
- 失败反馈归一化、自修复决策、schema 前置校验、Actor/Trace 透传、人工队列清理；
- 会话摘要 + 全局画像 + 显式记忆工具。

未做：
- 每个子 Agent 的独立熔断器/重试策略配置；
- 后台任务 worker（异步任务仍靠读接口/前端轮询推进）；
- 子 Agent SSE 流式消费与 `Last-Event-ID` 回放；
- 向量长期记忆、跨会话 RAG、记忆冲突消解；
- 标准 Google A2A（Agent Card / JSON-RPC / push notification）。

**一句话：**
> “现在的 A2A 不是‘调用失败就报错’，而是‘失败反馈 → 自动分析 → 追问/重试/换能力 → 最后才转人工’。记忆也不是黑盒，用户能看、能清、能解释边界。”
