# 02-技术选型与架构设计

> 项目：`wuye-agent`
> 版本：v0.1（设计稿）
> 日期：2026-11-20
> 状态：待评审
> 关联：`01-需求与功能模块清单.md`、`06-Agent接入与扩展规范.md`

---

## 1. 设计原则

1. **主 Agent 只做编排，不做领域业务**：领域规则、数据、工具留在子 Agent。
2. **凭据只在 Java 侧**：子 Agent 内部令牌、委托密钥不出 Java BFF，Python 只做推理。
3. **协议适配层隔离方言**：物业 0.7、合同 0.6 的差异全部收敛在 Adapter，核心域模型不被污染。
4. **能力命名空间化**：`capabilityId` 全局唯一，避免 `knowledge.search` 这类同名冲突。
5. **默认人类确认**：写操作必须用户显式同意，主 Agent 绝不自动确认。
6. **可降级**：单个子 Agent 故障不影响另一域；SSE 不可用自动降级轮询。
7. **可扩展**：新增标准 Agent 只做注册 + Manifest 同步，不改核心代码。
8. **数据隔离**：独立库/前缀/bucket，不直连子 Agent 存储。

## 2. 技术选型

### 2.1 总体选型

| 层 | 选型 | 版本建议 | 理由 |
|---|---|---|---|
| 主后端（BFF） | Java + Spring Boot | Java 21 / Spring Boot 3.5.x | 与现有子 Agent 生态一致；事务、审计、鉴权成熟 |
| Web 框架 | Spring MVC + SSE | 内置 | 单对话框需要 POST 流式，SSE 足够 |
| 安全 | Spring Security 6 + JWT | jjwt 0.12.x | 无状态、易与前端配合 |
| ORM | MyBatis-Plus | 3.5.x | 与 agent-gongdan 一致；复杂查询可控 |
| 迁移 | Flyway | 10.x+ | 版本化 DDL，禁止手工改库 |
| 数据库 | MySQL 8.0 | 共享实例 | 只使用独立库 `wuye_agent_db` |
| 缓存 | Redis 7（Lettuce） | 共享实例 | 前缀 `wuye_agent:`；会话缓存、确认令牌、分布式锁 |
| 对象存储 | MinIO | 共享实例 | 独立 bucket `wuye-agent` |
| 弹性 | Resilience4j | 2.x | 熔断、重试、限流、超时 |
| 文档 | springdoc-openapi | 2.x | API 清单可在线查看 |
| AI 服务 | Python + FastAPI | Python 3.13 / FastAPI 0.11x | 路由、槽位、生成；LLM 生态成熟 |
| LLM 客户端 | OpenAI SDK（DeepSeek 兼容） | 最新 | `deepseek-chat`，OpenAI 兼容接口 |
| 结构化输出 | Pydantic v2 | 2.x | 路由/槽位/生成结果校验 |
| 多步编排 | LangGraph（可选） | 1.x | 首期不引入；需要多步时再加 |
| 前端 | 原生 HTML/CSS/JS（ES Modules） | - | 无构建、易部署；符合项目偏好 |
| Markdown | marked + DOMPurify（本地 vendored） | 最新 | 安全渲染模型输出，不用 CDN |
| 测试（Java） | JUnit 5 + Mockito + WireMock | 最新 | Adapter 契约测试 |
| 测试（Python） | pytest + respx | 最新 | 路由/槽位单测 |
| 联调 | Mock Agent + curl 脚本 | - | 子 Agent 未启动时开发 |

### 2.2 明确不引入的东西

- 不新增 Docker / docker-compose 启动 MySQL、Redis、MinIO（共享中间件只读使用）。
- 不引入 Nacos/Consul 作为首期注册中心；Agent Registry 用 MySQL + 定时同步。
- 不引入 Kafka/RabbitMQ；首期异步靠子 Agent + 主 Agent 轮询/SSE。
- 不做微前端；单页原生前端足够。
- 不在 Python 侧保存子 Agent 凭据，也不让 Python 直连子 Agent。

### 3.1 关键边界

| 边界 | 规则 |
|---|---|
| 浏览器 ↔ Java | 只走主 Agent API；不出现子 Agent 地址、内部令牌、确认令牌 |

## 5. Agent 分层设计（核心）

### 5.1 分层结构

```text
agent/
├── model/                     # 统一领域模型
│   ├── AgentDescriptor
│   ├── Capability
│   ├── TaskRequest / TaskResult
│   ├── TaskEvent
│   ├── AgentError
│   └── Confirmation
├── registry/                  # 注册与发现
│   ├── AgentRegistryService
│   ├── ManifestSyncService
│   └── AgentHealthMonitor
├── catalog/                   # 能力目录
│   └── CapabilityCatalogService
├── adapter/                   # 协议适配 SPI
│   ├── AgentAdapter
│   ├── AbstractAgentAdapter
│   ├── PropertyMaintenanceAdapter
│   ├── ContractReviewAdapter
│   ├── GenericV1Adapter
│   └── AdapterRegistry
├── auth/                      # 凭据与委托
│   ├── CredentialProvider
│   ├── DelegationService
│   └── ActorMappingService
└── task/                      # 任务与确认
    ├── TaskGatewayService
    ├── TaskTrackerService
    ├── ConfirmationService
    ├── EventNormalizer
    └── TaskTimeoutScheduler
```

### 5.2 组件职责

| 组件 | 职责 | 不做什么 |
|---|---|---|
| `AgentRegistryService` | Agent CRUD、启停、状态、Manifest 缓存入口 | 不解析方言细节 |
| `ManifestSyncService` | 拉取/校验/快照 Manifest，更新能力目录 | 不执行业务任务 |
| `AgentHealthMonitor` | 定时探活，标记 `ENABLED/DEGRADED/DISABLED` | 不自动重启子 Agent |
| `CapabilityCatalogService` | 生成全局唯一能力目录，供路由与前端使用 | 不调用子 Agent |
| `AgentAdapter` | 方言翻译：提交/查询/确认/取消/事件/上传 | 不做路由决策 |
| `CredentialProvider` | 从环境变量/密钥引用读取每 Agent 凭据 | 不把明文写 DB/日志 |
| `DelegationService` | 签发/缓存委托令牌，按 Actor+Scope | 不转发内部令牌给前端 |
| `ActorMappingService` | 主用户 → 子 Agent Actor/Roles/Scopes | 不做权限放大 |
| `TaskGatewayService` | 统一任务入口、幂等、重试、状态归一化 | 不直接解析子 Agent 原始响应 |
| `TaskTrackerService` | 订阅/轮询事件、持久化、超时、取消 | 不生成自然语言 |
| `ConfirmationService` | 保管确认令牌、摘要、同意/拒绝 | 绝不自动确认 |
| `EventNormalizer` | 子 Agent 事件 → 统一 `TaskEvent` | 不丢 `seq`/去重信息 |

### 5.3 新增 Agent 的两种路径

| 路径 | 适用 | 工作量 |
|---|---|---|
| 标准 Agent（Canonical v1） | 新 Agent 按 `06` 的契约实现 | 注册 + Manifest 同步，**零代码** |
| 方言 Agent | 已有 Agent 协议不同（如物业 0.7、合同 0.6） | 新增一个 `AgentAdapter` 实现 + 注册 Bean |

> 关键：**Registry/Catalog/Task/Confirm/Event 全部复用**，新增 Agent 不碰核心流程。

## 7. 路由与会话状态机

### 7.1 路由管线

```text
用户消息
  → 归一化（去噪、引用解析、附件识别）
  → 规则路由（关键词 / 明确实体 / 当前会话域 sticky）
  → 若未命中或低置信度 → LLM 路由
  → 能力白名单校验（enabled + actor mapping + scope）
  → 槽位校验（缺失则追问）
  → 策略校验（写操作必须确认）
  → 执行任务
```

规则示例：

| 信号 | 目标域 |
|---|---|
| 工单、报修、派单、接单、现场、回访、SLA | `property` |
| 合同、条款、审查、风险、规则、甲方/乙方 | `contract` |
| 知识库、资料、制度（无域线索） | 追问 |
| 工单号 `GD...` | `property` |
| 合同号/合同 ID | `contract` |

置信度策略：

| 置信度 | 行为 |
|---|---|
| ≥ 0.85 | 直接执行只读；写操作进入槽位/确认 |
| 0.60–0.85 | 追问确认域/能力 |
| < 0.60 | 不调用子 Agent，给出能力引导 |

> LLM **只输出 JSON 决策**（`capabilityId`、`args`、`confidence`、`clarification`），不直接执行工具；Java 侧负责校验与执行。这样可防提示词注入导致的越权调用。

### 7.2 会话状态机

```text
IDLE
  → ROUTING
  → CLARIFYING（歧义）
  → SLOT_FILLING（缺参）
  → READY
  → EXECUTING
  → WAITING_CONFIRM
  → RUNNING
  → SUCCEEDED / FAILED / CANCELLED
```

状态持久化在 `wa_chat_message`、`wa_task_binding`、`wa_task_event`，进程重启可恢复。

## 8. 流式与事件

### 8.1 主 Agent SSE 事件

| event | 说明 | 关键字段 |
|---|---|---|
| `meta` | 本轮开始 | `sessionNo`、`messageNo`、`traceId` |
| `route` | 路由结果 | `capabilityId`、`confidence`、`router` |
| `delta` | 自然语言增量 | `content` |
| `task` | 任务卡片 | `taskNo`、`agentKey`、`status` |
| `confirm` | 确认卡片（不含 token） | `taskNo`、`summary`、`expiresAt` |
| `task_event` | 任务事件 | `seq`、`type`、`status`、`payload` |
| `done` | 本轮结束 | `messageNo`、`status` |
| `error` | 错误 | `code`、`message`、`retryable` |

### 8.2 降级策略

| 场景 | 降级 |
|---|---|
| 子 Agent SSE 不可用 | 轮询 `GET /tasks/{id}/events?afterSeq=` |
| 主 Agent SSE 断开 | 前端用最后 `messageNo/seq` 重连；服务端补发 |
| 子 Agent 健康检查失败 | 标记 `DEGRADED`，路由时提示并优先另一域 |
| LLM 超时 | 回退规则路由；仍失败则提示用户 |
| 确认令牌过期 | 任务置 `FAILED(CONFIRM_TIMEOUT)`，提示重新发起 |

## 9. 安全设计

1. **凭据分层**：每个子 Agent 独立 `INTERNAL_TOKEN` / `DELEGATION_SECRET`，只存环境变量或密钥引用，不写 DB、不写日志、不下发前端。
2. **确认令牌**：子 Agent 返回的 `confirmationToken` 只存 Redis（TTL 10 分钟，key `wuye_agent:confirm:{taskNo}`），浏览器只拿 `taskNo`。
3. **身份映射**：主用户 → 每个 Agent 的 `actorId/roles/scopes`；无映射时禁止写操作。
4. **最小权限**：能力级 scope；委托令牌按需签发，TTL 默认 10 分钟、最长 1 小时、不可再委托。
5. **SSRF 防护**：Agent `baseUrl` 仅允许配置白名单（`127.0.0.1` / 内网域名 + 允许端口），禁止用户输入 URL；禁止访问云元数据地址。
6. **输入安全**：文件类型/大小/魔数校验；Markdown 经 DOMPurify；SQL 全部参数化。
7. **审计**：登录、路由、任务提交、确认、取消、Agent 管理全部落审计；敏感字段脱敏。
8. **限流**：按用户/会话/能力限流；子 Agent 429 时带 `Retry-After` 退避。

## 13. 关键决策：逐个接入 vs 自定义 Agent

**结论：首期做“逐个接入 + 统一 Agent 层 + 声明式 Registry”，不做面向用户的自定义 Agent 创建器；P5 再做受控的自定义 Agent。**

### 13.1 为什么首期不选“自定义 Agent”

| 问题 | 说明 |
|---|---|
| 协议不统一 | 物业/合同方言不同；自定义 Agent 无法天然遵循同一契约 |
| 安全边界 | 用户自定义提示词/工具/URL 会引入越权、SSRF、数据外泄风险 |
| 审计责任 | 自定义 Agent 出错时难以界定责任与回滚 |
| 评测困难 | 没有稳定黄金集，无法保证路由与结果质量 |
| 路由可靠性 | 能力爆炸后 LLM 选择准确率下降，需要治理与配额 |

### 13.2 首期采用的分层方案

```text
接入层：Agent Registry（配置化）
协议层：AgentAdapter SPI（标准 Agent 零代码 / 方言 Agent 一个类）
能力层：CapabilityCatalog（命名空间 + JSON Schema）
执行层：TaskGateway/TaskTracker/Confirmation（复用）
```

新增一个标准 Agent 只需：

1. 在 Registry 注册 `agentKey/baseUrl/凭据引用`；
2. 同步 Manifest；
3. 勾选启用能力；
4. 配置身份映射；
5. 跑契约测试。

只有协议方言不同才需要写 Adapter。

### 13.3 P5 的“自定义 Agent”应该是什么

不是“让用户写任意 Agent 代码”，而是**受控模板**：

- 选择模板（知识问答 / 工单助手 / 合同审查助手）；
- 配置提示词、知识库、能力白名单；
- 配置配额、审批人、可见范围；
- 平台侧沙箱执行、版本化、评测后再发布；
- 与内置 Agent 共用路由、审计、确认、降级。

这样既保留扩展性，又不破坏安全与可运维性。
